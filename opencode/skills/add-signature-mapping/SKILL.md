# Add Signature Mapping

The single highest-volume auto-filed error in ecfx-backend ("Unable to determine county from Greenfiling Court Location: …") is fixed by **data work, not parser code**. This skill produces that fix correctly. Two chained mechanisms exist; a given ticket may need one or both.

## The two mechanisms

**A. Court-location → county (Greenfiling only, in code).**
`GreenfilingConstants.COURT_TO_COUNTY_MAP` — a generated, unmodifiable `Map<String,String>` of ~1,140 `map.put("<court location>", "<County>")` entries in `projects/receipt_processing/.../processors/email/providers/greenfiling/GreenfilingConstants.java`. Lookup is **exact-string** via `getCountyByCourtName(...)`, called from `GreenfilingEmailReceiptProcessor.getJurisdiction(...)` (~line 243), which throws `ReceiptEmailParseException` — the auto-filed error — when no entry matches. The header says it's generated by `generate_java_constants.py`, but **that generator is not in the repo** — edit the committed map directly, matching the existing entry style.

**B. County/signature → ECFX jurisdiction (all providers, in DB).**
Table `ecfx_provider_jurisdiction` (entity `com.goecfx.data.models.ProviderSignature`, composite key `provider_id` + `signature`). Runtime lookup: `BaseReceiptProcessor.getECFXJurisdictionForSignature(String)` → `JurisdictionNotFoundException` on miss. **Source of truth is the CSVs** at repo root `jurisdiction_metadata/`: `Jurisdictions.csv` (master list) plus one CSV per provider under `Providers/` (`Greenfiling.csv`, `Tylers_IL.csv`, `Tylers_TX.csv`, …; rows are `Jurisdiction ID,Signature`; the filename lowercased becomes the `provider_id`, e.g. `Tylers_IL.csv` → `tylers_il`). `jurisdiction_metadata/generate_sql.py` emits the Flyway migration (full DELETE + re-INSERT snapshot).

## Process

### 1. Extract the exact unmapped string

From the ticket/log, take the quoted value **verbatim** — the lookup is exact-string, so whitespace and punctuation matter. For Greenfiling that's the Court Location text; for Tyler it's the signature line (parsing handled by `SignatureHelper` / `ILSignatureUtil` etc. — if the signature is *parsed wrong* rather than *unmapped*, that's a code fix under `court-portal-processor-checklist`, not this skill).

### 2. Determine the target

- Greenfiling county: identify the real county for the court location (the location string itself usually names it; confirm against the court's site if ambiguous).
- Jurisdiction row: find the `Jurisdiction ID` in `jurisdiction_metadata/Jurisdictions.csv` that the signature should map to. If no jurisdiction exists at all, stop and flag — that's a product decision, not a mapping addition.

### 3. Apply the mapping

- **Mechanism A:** add `map.put("<exact string>", "<County>");` in `GreenfilingConstants.java`, placed with its county's neighbors, style-matched to adjacent entries.
- **Mechanism B (if the county/signature has no row for this provider):** append `<jurisdiction_id>,<signature>` to the provider's CSV, then run `jurisdiction_metadata/generate_sql.py` to regenerate the seed SQL as a **new** Flyway migration — never edit an applied `V*.sql`. Run the `flyway-migration-preflight` skill on the result (version collision check especially — these migrations are frequent).

### 4. Verify

- Exact-string check: `grep -F '<the string>' GreenfilingConstants.java` (or the CSV) — confirm no near-miss duplicate already exists (trailing space, different dash). If a near-duplicate exists, the bug may be upstream formatting drift; say so.
- There is **no dedicated unit test** for `COURT_TO_COUNTY_MAP` (Specs stub `getJurisdiction`), so validate by running the failing notice through `process-email-notice` if the `.eml` is available, or at minimum re-run the exact lookup in a scratch test.
- Note in the MR: `ProviderSignature` rows are cached (Caffeine, 5-day TTL via `CacheService.getProviderSignatures`) — DB-side additions may need a deploy/restart or cache window before taking effect in a long-running pod.

### 5. Deliver

One MR containing the map/CSV change (+ regenerated migration when mechanism B applies), referencing the Jira ticket and the exact string fixed. Cross-link the Greenfiling "Missing Signature Mappings" master-tracker ticket when applicable. Batch mode is encouraged: if the triage queue has several unmapped locations, fix them in one MR and list each string→county in the description.

## Quality bar

- The mapped string must be byte-for-byte what production logged — never "cleaned up".
- One concern per MR: mappings only; don't mix in parser changes.
- If the same location keeps arriving with *varying* text (dates, docket numbers embedded), mapping is the wrong fix — flag it as a normalization bug in the processor instead.
